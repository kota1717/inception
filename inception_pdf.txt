• プロジェクトの設定に必要なすべてのファイルは、srcs フォルダ内に配置してください。
• Makefile も必須であり、ディレクトリのルートディレクトリに配置する必要があります。
　この Makefile はアプリケーション全体を設定するものでなければなりません
（具体的には、docker-compose.yml を使用して Docker イメージを構築する必要があります）。
• 本課題では、受講者の背景によってはまだ学習していない概念を実践する必要があります。
  そのため、Dockerの使用に関する豊富なドキュメントを読むとともに
　課題を完了するために役立つあらゆる情報を積極的に参照することを強く推奨します。

本プロジェクトでは、特定のルールに基づいて構成された小規模なインフラストラクチャを設定することが求められます。
プロジェクト全体は仮想マシン環境内で実施する必要があります。Docker Composeを使用してください。

各 Docker イメージは、その対応するサービスと同じ名前でなければなりません。
各サービスは専用のコンテナー内で実行される必要があります。
パフォーマンスの観点から、コンテナーは Alpine または Debian の最終安定版の一つ前のバージョンから
ビルドする必要があります。選択は自由です。
また、サービスごとに独自の Dockerfile を作成する必要があります。各 Dockerfile は、Makefile によって
docker-compose.yml ファイル内で呼び出される必要があります。
これは、プロジェクトの Docker イメージを自分で構築する必要があることを意味します。
そのため、事前に作成された Docker イメージのプルや、DockerHub などのサービスの利用は禁止されています
（Alpine/Debian はこの規則の例外となります）。

次に、以下の設定が必要です：
• TLSv1.2 または TLSv1.3 のみをサポートする NGINX を含む Docker コンテナ
• WordPress + PHP-FPM のみを含む Docker コンテナ（nginx はインストールおよび設定不要）
• nginx を含まない MariaDB のみを含む Docker コンテナ
• WordPress データベースを格納するボリューム
• WordPress ウェブサイトファイルを含む第二のボリューム
• これら2つの永続ストレージには、Dockerの名前付きボリュームを使用する必要があります。
  バインドマウントは許可されていません。
• 両方の名前付きボリュームのデータは、ホストマシン上の/home/login/dataディレクトリ内に格納する
  必要があります。「login」の部分は、学習者のユーザー名に置き換えてください。
• コンテナ間の接続を確立するためのDockerネットワークが必要です。コンテナがクラッシュした場合には、
  自動的に再起動するようにしてください。


Dockerコンテナは仮想マシンではありません。そのため、'tail -f' や類似の手法に基づく不正なパッチ
を適用して実行することは推奨されません。デーモンの動作原理について理解し、
それらを使用するのが適切な方法かどうかを検討してください。


ネットワーク設定において「network: host」または「--link」オプション、あるいは「links:」の使用は
禁止されています。
docker-compose.ymlファイルには必ずネットワーク設定行を含める必要があります。
コンテナは無限ループを実行するコマンドで起動してはなりません。したがって、これはエントリーポイントとして
使用されるコマンドや、エントリーポイントスクリプト内で使用されるコマンドにも適用されます。
以下に禁止されている不正なパッチの例を挙げます：tail -f、bash、sleep infinity、while trueなど。

PID 1について、およびDockerfile作成におけるベストプラクティスについてお読みください。

• WordPressのデータベースには、2人のユーザーが存在する必要があります。そのうちの1人は管理者です。
管理者のユーザー名には、「admin」や「Admin」、「administrator」や「Administrator」を含める
ことはできません（例：admin、administrator、Administrator、admin-123など）。


Docker を使用すると、ボリュームはホストマシンの
/home/login/data フォルダにアクセス可能になります。もちろん、
「login」の部分はご自身のログイン名に置き換える必要があります。

手続きを簡略化するために、ドメイン名をローカルIPアドレスに紐付けるように設定する必要があります。
ドメイン名はlogin.42.frでなければなりません。ここでも、ご自身のログイン名を使用する必要があります。
例えば、ログイン名がwilの場合、wil.42.frはwilのウェブサイトを指すIPアドレスにリダイレクトされます。


最新のタグは禁止されています。Dockerfile にパスワードを含めてはいけません。環境変数の使用は必須です。
また、環境変数を保存するには .env ファイルを使用することも必須です。機密情報は Docker シークレットに
保存することを強くお勧めします。Git リポジトリに (適切に設定されたシークレット以外で) 見つかった認証情報、
API キー、またはパスワードは、プロジェクトの失敗につながります。
NGINXコンテナは、TLSv1.2またはTLSv1.3プロトコルを使用し、ポート443のみを介してインフラストラクチャへの
唯一のエントリポイントである必要があります。


セキュリティ上の理由から、認証情報、APIキー、パスワードなどは、様々な方法やファイルを用いてローカルに保存し、
Gitでは無視されるようにする必要があります。公開された認証情報は、プロジェクトの失敗に直結します。

環境変数ファイル（.envなど）に、変数名（ドメイン名として）を保存できます。


既存の要件に加え、以下のドキュメントファイルを
リポジトリのルートディレクトリに配置する必要があります。これらはMarkdown形式（.md）で記述されている必要が
あります。

• USER_DOC.md — ユーザードキュメント このファイルでは、エンドユーザーや管理者が以下の操作を
どのように行うかを、明確かつ平易な言葉で説明する必要があります：
◦ スタックによって提供されるサービスの内容を理解する。
◦ プロジェクトを起動および停止する。
◦ ウェブサイトおよび管理パネルにアクセスする方法。
◦ 認証情報を確認・管理する方法。
◦ サービスが正しく実行されていることを確認する方法。

• DEV_DOC.md — 開発者向けドキュメント このファイルには、開発者が以下の操作を行う方法を記述する必要があります：
◦ 環境をゼロからセットアップする方法（前提条件、設定ファイル、シークレット）。
◦ Makefile および Docker Compose を使用してプロジェクトをビルドおよび起動する方法。
◦ 関連するコマンドを使用してコンテナおよびボリュームを管理する方法。
◦ プロジェクトデータがどこに保存され、どのように永続化されるかを特定する方法



Step 1: インフラ・環境の基盤作成（ディレクトリ構造 & ドメイン設定）
まずは 42 のルール（.env の使用、特定ディレクトリ構造、ホスト環境の設定）を整えます。

/etc/hosts の設定: Host OSの /etc/hosts に 127.0.0.1 login.42.fr（自分のログインID）を追加。

ディレクトリ構造の作成: 規定のフォルダ構成（srcs/, srcs/requirements/mariadb など）を準備。

データ永続化用フォルダの作成: 主に /home/login/data/wordpress や /home/login/data/mariadb などのバインドマウント用ディレクトリを作成。

Step 2: 各サービスの Dockerfile と設定ファイルの個別構築
依存関係の下流（データベース）から順番に1つずつビルド＆単体動作確認を行います。

MariaDB (Database)

やること: Debian（またはAlpine）ベースの Dockerfile 作成、初期化スクリプト（.sh）でデータベースとユーザーを作成。

単体検証: docker build & docker run で起動し、コンテナ内に入って mariadb -u user -p でログイン・DBが生成されているか確認。

WordPress + php-fpm (Application)

やること: wp-cli を導入し、php-fpm の設定（www.conf で listen = 9000 に設定）を行うスクリプトを作成。

単体検証: MariaDB コンテナと同一ネットワーク（またはリンク）で繋ぎ、wp core config や wp core install が自動で通るか確認。

NGINX (Web Server)

やること: OpenSSL で自己署名証明書（TLS v1.2/v1.3）を発行する設定、default.conf で Port 443 のリバースプロキシ（fastcgi_pass wordpress:9000;）を設定。

単体検証: ブラウザや curl -k [https://login.42.fr](https://login.42.fr) でアクセスし、TLS接続および PHP 実行結果が返るか確認。

Step 3: docker-compose.yml による連携
単体で動くことが確認できたら、いよいよ docker-compose にまとめます。

docker-compose.yml の記述:

各サービスの build パス、image 名、container_name を設定。

networks: 3つのコンテナが所属する専用内部ネットワークを設定。

volumes: ホストの永続化フォルダ（MariaDB用、WordPress用）をマウント。

env_file: .env から環境変数を読み込むよう指定。

restart: always などの規定ポリシーを追加。

動作確認: docker compose up --build を実行し、全コンテナが正常に連動して起動するか確認。

Step 4: Makefile の作成・仕上げ
最後に、評価時に一発で操作できるように Makefile を作成します。

必須ターゲットの作成:

all: データ保存用ディレクトリの作成 ＋ docker-compose up --build -d

down: docker-compose down

clean: コンテナ・イメージの削除

fclean: 永続化データ（volumens）の削除を含めた完全クリーンアップ

re: fclean ＋ all
